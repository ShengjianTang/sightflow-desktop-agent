## 已实现行为

- 视觉定位与回复模型分开：设置 → 智能体 → 硅基流动多模态 → 回复模型。留空继续跟随视觉模型；定位、布局和图片工具使用原视觉模型。
- 右侧会话面板裁剪保留标题、消息和编辑框，模型坐标映射回原窗口。本地原图继续用于发送检查，未改变未读检测阈值或联系人定位。
- 模型以有序消息列表为唯一证据来源；最新消息与发送方由宿主派生。avatarBbox 与旧 senderBbox 兼容但冲突即拒绝，校验失败最多纠正一次，不能通过删掉后续消息规避校验。
- 当前答案冻结；生成期间新增对方消息经发送前追加关系复核后排入下一批。先答 A，再答 B；即使 B 在 A 的回复上方、A 已滚出视区，仍按宿主记录的边界处理。模糊重复消息没有可靠边界时保守拒绝，不凭文字相同猜测身份。
- 会话切换、人工回复、人工草稿、未知发送方、头像像素不支持、缺少完整顺序时不发送。草稿清空会触发重新观察待回复批次。
- 停止信号传递到网络读取和桌面输入检查；晚到结果不发送，已粘贴或已按 Enter 的事件不自动重发。
- 性能轨迹仅增加批次 ID、阶段、模型、错误码和耗时，不新增聊天正文或凭证日志。既有 worktrace 截图策略保留。

## 真实微信验收

1. 完全退出旧 SightFlow；在原工作区执行 `npm start`。使用专用测试会话，用户自行触发引擎和消息，不以普通联系人作为测试对象。
2. 完成至少 30 个可回复批次，覆盖短句、连续消息、图片、表情，以及生成期间继续发 B。检查 A/B 是否分别得到回复、是否重复或漏答；另独立测试草稿、手动回复、切换联系人和停止。
3. 为每个应回复批次记录 sessionId、batchId、最后一条消息实际可见时间（Unix 毫秒或带 +08:00 的 ISO 时间）。存为本地 markers.json 数组，字段为 `sessionId`、`batchId`、`lastMessageVisibleAt`。不要填造的时间。批次 ID 在日志和 trace.performance 中可见。
4. 执行：

```powershell
node scripts/reply-latency-report.cjs "<用户数据目录>/worktrace/sessions/<sessionId>/trace.jsonl" --markers "<markers.json>"
```

没有外部时间标记时只输出阶段耗时，不宣称端到端达标。标记了却未完成的批次计为不完整，阻止通过；至少 30 批全部完成，中位 ≤8 秒、P95 ≤15 秒只是速度门槛，准确性还需用户验收。

若需要再次运行模型测试，先选新的 REPLY_BENCHMARK_RUN 目录，再执行 `node scripts/reply-benchmark.cjs --prepare` 和 `node scripts/reply-benchmark.cjs`。这会产生模型 API 请求费用，但不操作微信、不修改配置。现有三轮原始结果保留在 .local/ 中。
